## 三、同步规则

### main → mves (技术下沉)

| 内容 | 频率 | 方式 |
|------|------|------|
| LLM 模块更新 | 按需 | `git checkout main -- moss/core/` |
| Bug 修复 | 立即 | cherry-pick 提交 |
| 文档改进 | 每周 | 手动同步 |
| 稳定功能 | 每月 | 分支合并 |

**示例**:
```bash
# 同步 LLM 模块到 mves
cd moss-mves
git checkout main -- moss/core/llm_backend.py
git checkout main -- moss/core/llm_mutator.py
```

---

### mves → main (技术上升)

| 内容 | 频率 | 方式 |
|------|------|------|
| 统计验证报告 | 完成后 | PR 合并文档 |
| 大规模实验数据 | 完成后 | 同步到 `experiments/` |
| 稳定新功能 | 验证后 | PR 合并代码 |
| 技术报告 | 发布时 | 同步到 `docs/` |

**示例**:
```bash
# 同步 N=45 报告到 main
cd moss
git checkout mves -- docs/mves/PHASE2_FINAL_REPORT.md
cp docs/mves/PHASE2_FINAL_REPORT.md docs/MOSS_PHASE2_N45_STATISTICAL_VALIDATION.md
```

## 五、冲突处理

### 代码冲突

**策略**: 小步提交，频繁同步

```bash
# 避免冲突的最佳实践
1. 每天 pull 对方分支最新代码
2. 功能开发在独立分支进行
3. 完成后立即同步到目标分支
4. 大改动前先沟通
```

**解决流程**:
```bash
# 1. 更新本地
git checkout main
git pull origin main

git checkout mves
git pull origin mves

# 2. 尝试同步
git checkout mves
git merge main --no-commit

# 3. 解决冲突
# 手动编辑冲突文件...

# 4. 完成合并
git add <resolved files>
git commit -m "merge: main → mves (同步 LLM 模块)"
git push origin mves
```

## 六、决策机制

### 技术决策

| 决策类型 | 决策者 | 咨询对象 |
|----------|--------|----------|
| main 分支功能 | main 维护者 | mves 团队 |
| mves 分支实验 | mves 团队 | main 维护者 |
| 跨分支同步 | 双方协商 | - |
| 版本发布 | 双方共同 | - |

### 同步决策

**自动同步** (无需协商):
- Bug 修复
- 文档更新
- 统计数据

**需要协商**:
- 破坏性改动
- 大规模重构
- API 变更

## 七、长期策略

### 选项 A: 永久双分支 (推荐) ⭐

**优点**:
- main 保持稳定，适合生产
- mves 自由探索，适合研究
- 降低风险，互不影响

**缺点**:
- 需要维护两个分支
- 同步工作量大

**适用场景**:
- 长期研究项目
- 需要稳定版本
- 团队分工明确

---

### 选项 B: 最终合并

**时机**:
- mves 技术成熟 (v8.2.0+)
- 充分验证完成
- 社区反馈积极

**方式**:
- mves 合并到 main
- main 作为唯一主线
- 创建 `legacy` 分支保留旧代码

**优点**:
- 简化维护
- 集中资源
- 统一社区

**缺点**:
- 失去实验田
- 合并风险高

---

### 选项 C: 多分支生态

**演进**:
- main: 稳定版 (LTS)
- mves: 开发版 (滚动更新)
- feature/*: 实验性功能

**适用**: 项目壮大后 (贡献者>10)
