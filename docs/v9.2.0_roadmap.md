# MOSS v9.2.0 Roadmap: Cross-File Refactoring & Production Deployment

**Target Release:** 2026 Q2  
**Theme:** Production-Grade Codebase Evolution  
**Status:** Planning Phase

---

## Executive Summary

v9.2.0 will transform MOSS from a single-file refactoring tool into a comprehensive codebase evolution platform capable of cross-file transformations, production deployment management, and enterprise-grade monitoring.

**Key Deliverables:**
- Cross-file refactoring (function moving, module reorganization)
- Production deployment toolkit (configuration, monitoring, CLI)
- Performance optimizations (incremental analysis, parallel processing)
- Developer experience enhancements (CLI toolchain, IDE plugin API)

## 1. Cross-File Refactoring Engine

### 1.1 Motivation

Current limitation: MOSS v9.1 operates on single files. Real-world refactoring often requires:
- Moving functions between modules
- Splitting large modules into packages
- Merging duplicate code across files
- Reorganizing package structure

### 1.2 Technical Design

#### Architecture

```
CrossFileRefactorEngine
├── DependencyAnalyzer
│   ├── ImportGraphBuilder      # Build module dependency graph
│   ├── SymbolTracker           # Track function/class usage across files
│   └── ImpactAnalyzer          # Analyze refactoring impact scope
├── TransformationPlanner
│   ├── MovePlanner             # Plan function moves
│   ├── SplitPlanner            # Plan module splits
│   └── MergePlanner            # Plan code merging
├── SafetyValidator (Extended)
│   ├── CrossFileSyntaxCheck    # Validate all affected files
│   ├── ImportConsistencyCheck  # Ensure imports remain valid
│   └── ReferenceIntegrityCheck # Verify all references updated
└── TransactionManager
    ├── ChangeBatch             # Atomic batch of changes
    ├── RollbackSupport         # Full rollback capability
    └── GitIntegration          # Automatic git commits
```

#### Core Capabilities

| Refactoring Type | Description | Complexity |
|------------------|-------------|------------|
| **Move Function** | Move function to different module | Medium |
| **Move Class** | Move class with dependencies | High |
| **Extract Module** | Split large module into package | High |
| **Merge Modules** | Combine related modules | Medium |
| **Rename Symbol** | Rename with cross-file updates | Low |
| **Optimize Imports** | Remove unused, organize across files | Medium |

## 3. Performance Optimizations

### 3.1 Incremental Analysis

**Problem:** Full codebase analysis is slow for large projects.

**Solution:** Only analyze changed files since last run.

```python
class IncrementalAnalyzer:
    def __init__(self, cache_dir: Path):
        self.cache = AnalysisCache(cache_dir)
        self.checksum_calculator = ChecksumCalculator()
    
    def analyze(self, codebase: Codebase) -> AnalysisResult:
        changed_files = self.get_changed_files(codebase)
        cached_results = self.cache.get_unchanged(codebase)
        new_results = self.analyze_files(changed_files)
        return self.merge_results(cached_results, new_results)
    
    def get_changed_files(self, codebase: Codebase) -> List[Path]:
        """Compare checksums to find changed files"""
        changed = []
        for file in codebase.files:
            current_checksum = self.checksum_calculator.calculate(file)
            cached_checksum = self.cache.get_checksum(file)
            if current_checksum != cached_checksum:
                changed.append(file)
        return changed
```

### 3.2 Parallel Processing

```python
class ParallelRefactorEngine:
    def __init__(self, max_workers: int = 4):
        self.executor = ProcessPoolExecutor(max_workers=max_workers)
    
    async def refactor_batch(
        self,
        files: List[Path],
        strategies: List[RefactorStrategy]
    ) -> List[RefactorResult]:
        """Process multiple files in parallel"""
        tasks = [
            self.executor.submit(self.refactor_file, file, strategies)
            for file in files
        ]
        results = await asyncio.gather(*tasks)
        return results
```

### 3.3 Caching Strategy

| Cache Type | Content | TTL | Size |
|------------|---------|-----|------|
| AST Cache | Parsed ASTs | 1 hour | 100MB |
| Analysis Cache | Issue detection results | 24 hours | 500MB |
| LLM Response Cache | LLM refactoring outputs | 7 days | 1GB |
| Import Graph Cache | Module dependencies | 1 hour | 50MB |

## 4. Developer Experience

### 4.1 IDE Plugin API

```python
# moss/ide/api.py

class IDEPluginAPI:
    """API for IDE integrations (VSCode, PyCharm, etc.)"""
    
    def analyze_current_file(self, file_path: Path, content: str) -> List[Issue]:
        """Analyze the currently open file"""
        analyzer = CodeAnalyzer()
        return analyzer.analyze_content(content, file_path)
    
    def get_quick_fixes(self, issue: Issue) -> List[QuickFix]:
        """Get available quick fixes for an issue"""
        fix_provider = QuickFixProvider()
        return fix_provider.get_fixes(issue)
    
    def apply_quick_fix(self, fix: QuickFix, document: Document) -> Edit:
        """Apply a quick fix to the document"""
        return fix.apply(document)
    
    def on_file_save(self, file_path: Path) -> Optional[RefactorSuggestion]:
        """Hook called when file is saved"""
        if self.config.refactor_on_save:
            return self.suggest_refactoring(file_path)
        return None
```

## Appendix: Technical Decisions

### ADR-001: Graph Database for Dependencies
**Decision:** Use NetworkX in-memory graphs, not external DB  
**Rationale:** Simpler deployment, sufficient for typical projects (<10k files)

### ADR-002: Transaction Format
**Decision:** Git-based transactions with automatic commits  
**Rationale:** Familiar to developers, built-in rollback

### ADR-003: Configuration Format
**Decision:** YAML with JSON schema validation  
**Rationale:** Human-readable, widely supported, type-safe
